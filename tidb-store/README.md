# @cvmind/tidb-store

Runs CVMind's Mongoose models on TiDB (MySQL-compatible) tables instead of MongoDB. The models, validation, defaults, hooks and every `Model.find()` / `.save()` call in the app stay as they are. Only the layer under Mongoose that talks to the database changes.

## Turning it on

```
DATABASE_DRIVER=tidb
TIDB_DATABASE_URL=mysql://USER.root:PASSWORD@HOST:4000/cvmind
```

`backend/src/db.js` and the agent worker call `connectDatabase(mongoose)`. To go back to MongoDB, unset `DATABASE_DRIVER` (with `MONGODB_URI` set).

## How it works

```
Model.find() ──▶ Mongoose (casting, validation, hooks) ──▶ SqlCollection ──▶ TiDB
```

- `connectTidb()` opens a small mysql2 pool and puts a `SqlDb` where Mongoose expects the MongoDB driver's `Db`. Each collection is a `SqlCollection` with the driver methods Mongoose and the app call: `find`, `findOne`, `insertOne/Many`, `updateOne/Many`, `replaceOne`, `findOneAndUpdate/Delete/Replace`, `deleteOne/Many`, `countDocuments`, `distinct`, `aggregate`, `bulkWrite`.
- **Tables** come from `schema/plan.json` and `schema/schema.sql`, generated by `db-migration/plan.mjs` from the Mongoose models and the real data:
  - nested objects become columns (`contact.email` → `contact__email`)
  - lists of objects become child tables (`teamtasks__checklist`, with `parent_id` → parent and `ON DELETE CASCADE`)
  - lists of plain values, Mixed and Map fields become JSON columns
  - embeddings become `VECTOR(768)` columns with HNSW indexes
  - each table has `_extra JSON` for any value without a column, so nothing is ever dropped
- **Filters** (`filter.js`) become SQL `WHERE` where the meaning is identical: equality, `$in/$nin/$ne`, ranges, `$or/$and`, list membership (`MEMBER OF`), and fields inside lists of objects (`EXISTS` on the child table). Anything else (regex, `$type`, `$size`, `$elemMatch`...) is checked in JS with [mingo](https://github.com/kofrasa/mingo) after a looser SQL prefilter, so results always match MongoDB.
- **Updates** lock the matching rows (`SELECT ... FOR UPDATE`), apply the MongoDB update operators in JS (mingo), and write only the columns and child tables that changed, in one transaction.
- **Duplicate keys** raise MongoDB's `E11000` error (`code: 11000`), which app code and Mongoose already handle.
- **Aggregations** load the documents matched by the first `$match` stage (filtered in SQL) and run the pipeline with mingo.
- **Files** (resume PDFs, agent artifacts) use `TidbGridFSBucket`, which keeps GridFS's files/chunks layout.

## Changing a model

A new field needs a column. Until it has one it is stored in `_extra` and still reads back correctly, but cannot be filtered in SQL or indexed. To add columns:

```
cd db-migration
npm run introspect && npm run scan && npm run plan   # regenerates schema.sql and tidb-store/schema/
```

Then apply the new columns to TiDB with `ALTER TABLE` (compare the new `schema.sql` with the live table).

## Tests

```
node --test tidb-store/test/adapter.test.js          # adapter tests on <db>_test
cd backend && TEST_DATABASE=tidb npm test             # the backend suite on TiDB
cd auto-apply-agent && TEST_DATABASE=tidb npm test    # the agent suite on TiDB
```

Tests use `TIDB_TEST_DATABASE_URL`, or `TIDB_DATABASE_URL` with the database renamed to `cvmind_test`. Wiping data is refused on any database whose name does not end in `_test`. Create the test tables with `node tidb-store/scripts/setup-test-db.mjs`.

## Limits

- No change streams, sessions or multi-document transactions through Mongoose (CVMind uses none).
- Aggregation-pipeline updates (`updateOne(filter, [ ... ])`) are not supported.
- Aggregations and regex searches read the matching rows into memory. Fine at CVMind's size; move hot ones to SQL if a collection grows large.
